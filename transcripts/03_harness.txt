⏺ Read all of docs/ and data/. My recommendation: code handles the numbers and
  keeps the records, and the model handles judgment. Deterministic code never
  guesses. The model never does arithmetic and never edits source data. The two
  meet in one shared, versioned belief store.

  The core idea: compute tools read their settings from memory

  What makes this flexible is that the compute code doesn't hard-code mappings,
  unit sizes, schedules or fixes. It reads them from the belief store. When the
  model finds something new, it records a belief, and the next compute run uses
  it, with the source attached.

  Example from this packet:
  1. reconcile(chicken) → returns unmapped SKU AW-CHK20: 11 cases (INV-013, 016,
     099) excluded
  2. The model reads CAT-CHICKEN20 and N11 and records: AW-CHK20 → chicken, 20 
     lb/case, kind=inferred, sources=[CAT-CHICKEN20, N11]
  3. It reruns reconcile. Chicken purchases now include those cases, and the
     output shows that a mapping inferred by the model was used.

  The same loop handles:
  - the INV-010 pepper price of 210.00 (probably 21.00)
  - the stale delivery days for Alder (vendor V1), where N09 overrides
    vendors.csv
  - the M99 Weekend special, which has no recipe
  - INV-099, entered as received but due for delivery Oct 6

  None of these fixes lives in Python or in the prompt. Each is a belief with
  sources that can be withdrawn later.

  Data layers

  1. Evidence (never changed). Load the CSVs into SQLite as they are, plus a
  notes table built from the log. The original IDs (row_id, invoice_id, N01…)
  become the keys. Nothing ever writes here.

  2. Beliefs (append-only, tracks two dates). One table:
  claims(id, subject, predicate, value JSON,
         valid_from, valid_to,           -- when it's true in the world
         recorded_at, status,            -- when we learned it: 
  active|superseded|retracted|disputed
         kind,                           -- observed|reported|inferred|assumed
         sources[], supersedes, author)  -- author: loader|model|user
  questions(id, subject, text, blocks[], sources[], status, resolved_by)
  - subject/predicate are free strings (sku:AW-CHK20 / maps_to, vendor:V1 /
    delivery_days, invoice:INV-099 / physically_received). New kinds of fact
    need no schema migration.
  - Facts that change, like chicken going from $3.20 to $3.65 on Sep 28, are
    just two claims with different valid_from dates. Nothing is overwritten.
  - kind is how answers separate evidence from inference.

  3. Corrected views (pure code). effective_invoice_lines, effective_vendors,
  and so on: the original evidence with active correction claims applied on top.
  Every compute tool reads these views. Each output row lists the corrections
  that touched it.

  Guardrails (small Python checks, not judgment):
  - Reject writes whose source IDs don't exist.
  - When two active claims about the same subject and predicate overlap in time,
    mark them disputed and open a question. Code detects the conflict; the
    model decides which claim wins.
  - Check every number in the final answer against tool outputs.

  System prompt: principles, not traps

  Don't list the traps in the prompt ("watch out for the INV-010 price"). The
  model should find them, or flexibility is fake. The prompt should cover:
  - Context: "now" is Oct 5, 06:00 ET; Maya places orders and Theo reads the
    summary; the records are incomplete and may disagree.
  - Handling evidence:
    - Cite IDs.
    - Label each statement as observed, reported, inferred or assumed.
    - A newer report from the person who checked beats an older one.
    - A physical check beats an office entry.
    - A dated note beats a stale reference sheet.
    - If unsure, open a question instead of picking a side.
  - Workflow: recall memory → query → compute → check for conflicts → write
    durable facts.
  - Memory rule: store only what would change a future answer or calculation,
    such as mappings, schedules, corrections, retractions and open questions.
    Don't store calculated results, because they can be recomputed.
  - Output: the answer first, then the evidence, then the unknowns.

  Two run modes, one agent

  - Two writers (loader and model): the loader writes only observed claims from

⏺ You're right. The last version was built around specific rows in this packet.
  Below is a general set of tools: what a restaurant ops agent would need for
  any site and any week. This packet's issues should come up as outputs of these
  tools, not be designed into them.

  Foundation (not tools)

  One normalized model, built by the loader:
  - Entities: ingredient, menu item, vendor, SKU
  - Mapping table: SKU → ingredient, with units per pack (taken from the
    catalog)
  - Event tables: sales, purchases, counts, notes. Every row keeps its source
    ID, a date, and a base-unit quantity.

  Every tool below works on this model. Adding a site or vendor means adding
  mappings, not code.

  Tools (7)

  Read

  1. query(sql)
  Read-only SQL over the normalized model and memory. Fallback for questions the
  other tools don't cover.

  2. search_notes(text?, since?, entity?)
  Unstructured context: notes, messages, later emails. Returns note IDs and
  text.

  Analyze (deterministic, every result cites source IDs)

  3. metrics(names[], period, grain, group_by?)
  One tool over a catalog of defined measures:
  - sales (dollars, units, mix)
  - purchase spend
  - unit cost
  - expected usage (recipe × sales)
  - actual usage (counts + purchases)
  - variance
  - purchases ÷ sales

  Supports compare_to for comparing two periods. The catalog grows; the tool
  doesn't change.

  4. detect_anomalies(period, scope?)
  Runs a list of general checks. Each finding has a check type, severity, the
  entity and the evidence IDs. Checks:
  - Price: unit price out of line with this SKU's history or the catalog
  - Quantity: order or sales quantity far outside the usual range
  - Totals: invoice line totals don't add up to the header total
  - Status: marked received but the delivery date is in the future, or a note
    disputes it
  - Mapping: unknown SKU, unit or pack size
  - Coverage: an item is selling with no recipe, or with an expired recipe
  - Usage: actual vs. expected usage beyond tolerance
  - Staleness: reference data older than a set age, or contradicted by a newer
    note

  5. project(entities[], through_date, assumptions{})
  Looks forward: stock on hand + expected deliveries − forecast use, set against
  vendor deadlines. Assumptions such as a demand boost or the delivery schedule
  are passed in and repeated in the output. Returns days of stock left, any
  stockout date, and the date each order must be placed.

  Memory

  6. recall(entity?, kind?, as_of?, include_history?)
  Lists facts, open questions and to-dos, current or as of a past date.

  7. remember(kind, entity, statement, sources[], effective_from?, supersedes?)
  Writes one item. kind is fact, question or to-do. A change creates a new
  version, and the old one is marked replaced or retracted. The tool rejects
  sources that don't exist.

  How "What changed last week, and should I care?" works

  The model calls:
  1. metrics([sales, mix, spend, unit_cost, usage_variance], last_week, 
     compare_to=prior_week) to get the changes across every signal
  2. detect_anomalies(last_week) to find data-quality and operational problems
  3. recall(since=last_week) to see which beliefs changed: supplier, schedule or
     menu facts, and open questions
  4. search_notes(since=last_week) for anything not yet in memory

  Then it ranks by money at stake, deadline, and whether an item makes other
  numbers unreliable. It cites IDs and labels each point as evidence or
  inference.

  Where the intelligence sits

  - Code: units, arithmetic, general checks, versioning. Same rules for every
    restaurant.
  - Model:
    - choosing which tools to run
    - judging whether something matters
    - reconciling conflicting sources (note vs. invoice status)
    - deciding what to remember
    - saying what's unknown

  The prompt holds how to judge evidence, not facts about this packet.

⏺ Agreed. The previous set mixed levels: raw SQL next to tools for specific
  analyses, with no shared model underneath. A cleaner design starts with one
  data model and gives each verb (read, query, edit, analyze) one tool.

  Data model: three types, one shape

  entity   id, type (ingredient|item|vendor|sku|person), name, aliases[]
  record   id (source ID), type 
  (sale|invoice|invoice_line|count|recipe|menu|catalog|vendor_sheet|note),
           date, refs{ingredient, item, vendor, sku, invoice}, fields{...}     ←
  never changed
  fact     id, about (entity or record ID), key, value, kind 
  (fact|question|todo),
           valid_from, status (active|superseded|retracted), sources[], 
  supersedes, author

  The rule that makes reads and edits work together: reads return the effective
  view, meaning the record with any active facts about it applied on top. Each
  value shows where it came from:

  INV-010-L01.unit_price = 21.00   (from fact F12, sources [INV-010-L01, 
  CAT-PEPPER]; original 210.00)
  vendor:V1.delivery_days = Mon/Wed (from fact F7, source N09; original Mon/Thu 
  in vendors.csv)

  Edits never touch records. They add facts, and every read picks those facts
  up.

  Tools: 6, one per verb

  ┌────────────┬───────────┬────────────────────────────────────────────────┐
  │    Verb    │   Tool    │                   Signature                    │
  ├────────────┼───────────┼────────────────────────────────────────────────┤
  │            │           │ get(ids[], as_of?) returns one or more         │
  │ Read       │ get       │ records, entities or facts, with linked items  │
  │            │           │ (invoice → its lines, fact → its sources,      │
  │            │           │ entity → its aliases)                          │
  ├────────────┼───────────┼────────────────────────────────────────────────┤
  │            │           │ find(type, where{refs, date range, field ops}, │
  │ Query      │ find      │  as_of?, limit?) returns effective records.    │
  │            │           │ One filter syntax for every type.              │
  ├────────────┼───────────┼────────────────────────────────────────────────┤
  │            │           │ aggregate(type, measure, group_by[], period,   │
  │ Analyze    │ aggregate │ grain?, compare_to?) returns sums, counts or   │
  │ (generic)  │           │ averages with the contributing IDs. Uses the   │
  │            │           │ same filters as find.                          │
  ├────────────┼───────────┼────────────────────────────────────────────────┤
  │ Analyze    │ compute   │ compute(name, params), a registry of named     │
  │ (domain)   │           │ domain calculations (below)                    │
  ├────────────┼───────────┼────────────────────────────────────────────────┤
  │            │           │ assert(about, key, value, kind, sources[],     │
  │ Edit       │ assert    │ valid_from?, supersedes?) adds a fact.         │
  │            │           │ Corrections, mappings, schedules, questions    │
  │            │           │ and to-dos all go through it.                  │
  ├────────────┼───────────┼────────────────────────────────────────────────┤
  │ Edit       │ retract   │ retract(fact_id, reason, sources[])            │
  └────────────┴───────────┴────────────────────────────────────────────────┘

  There's no raw SQL. find + aggregate cover ad-hoc questions, and the results
  stay effective and cited.

  compute registry

  These need domain knowledge aggregate can't express. Each is a pure function
  over effective records, so facts written with assert change its results
  automatically.

    ingredient and period

    and IDs. Checks cover:
    - price vs. history
    - quantity outliers
    - line totals vs. header total
    - status vs. date
    - unmapped references
    - items selling with no recipe
    - stale reference data
  - project: stock on hand + scheduled deliveries − forecast use, with stated
    assumptions
  - item_cost: ingredient cost per portion vs. menu price

  New capabilities are new registry entries. The tool surface stays the same.

  Example: "What changed last week, and should I care?"

  1. aggregate(sale, net_sales, [item], last_week, compare_to=prior) for sales
     and mix
  2. aggregate(invoice_line, spend, [ingredient], last_week, compare_to=prior)
     for purchasing
  3. compute(usage, {period: last_week}) for inventory variance
  4. compute(scan, {period: last_week}) for anomalies
  5. find(fact, {recorded_since: last_week}) for beliefs that changed
  6. find(note, {since: last_week}) for context not yet captured
  7. The model ranks the results and may call assert on new facts or questions.
     Every claim cites IDs.

  Why this holds up in production

  - One data model: a new source (another POS, emailed invoices) is just a
    loader that writes records and entities.
  - Consistent edits: corrections, entity resolution and changed facts all use

  - Uniform reads: effective view, as_of, and where each value came from work
    the same everywhere.
  - Scoped intelligence: the model chooses tools, interprets results and decides
    what to write. Code never guesses, and the model never does arithmetic.

  The test: if two reasonable operators could disagree, it belongs to the model.

  Revised data layer: facts only

  Keep (pure normalization, no opinions):
  - purchases: delivery date, vendor, ingredient, base qty, cost, price per base
    unit, entered status, line ID
  - sales: date, weekday, item, qty, net sales, row ID
  - recipe_use: date, ingredient, expected qty, item, recipe row ID (items with
    no recipe simply have no rows)
  - counts, recipes, menu, vendor_sheet, catalog: cleaned copies of the source

  - notes: full text, author, timestamp
  - memory

  Remove:
  - issues: the model finds problems itself.
  - stock_outlook: the model builds the forecast and owns the assumptions.
  - stock_reconciliation and weekly_summary: one SQL query each; the model
    writes them.
  - Memory overrides inside views: the model reads the data and memory side by
    side and decides which to use.

  Memory becomes the model's notebook

  - key is free text, with suggestions, not a fixed list. The model decides
    what's worth recording.
  - New kind, hypothesis: "Chicken gap likely includes Sep 22 waste (N06)," with
    a stated confidence. Hypotheses can be confirmed or dropped later. This is
    what makes memory reasoning, not just a record of facts.
  - Conflicts aren't settled by code. Code only refuses to save a second active
    belief on the same subject without the model explicitly saying which one it
    replaces or that it's keeping both and opening a question.

  Tools: still 3, slightly more open

  - sql(query): read-only over the fact tables and memory.
  - recall(about?, include_history?)
  - remember(op, about, key, value, kind, sources, confidence?, valid_from?, 
    valid_to?, target_id?, reason?)

  Optionally, python(code) for forecasts or ranges that are awkward in SQL.

  How the flows change

  Morning brief (the biggest change): instead of reading issues, the model works
  through a loose plan from the prompt:
  1. Compare this week to last.
  2. Reconcile each ingredient.
  3. Read new notes.
  4. Check what's due before the next order deadlines.

  Then it forms its own hypotheses, checks them with SQL, and ranks. It might
  find INV-010, or it might decide that INV-099 matters more. That's judgment.

  "What changed last week": the model writes its own week-over-week queries
  across purchases, prices, usage gaps and notes, then explains what matters.

  "Before Saturday": the model chooses the demand baseline, decides how to
  handle N15 ("busier, no numbers"), and states the range it assumes.

  What you give up

  - Consistency: two runs may rank differently, or miss something.
  - Cost and latency: more tool calls per question, roughly 5–15 per brief
    instead of 2–4.

  Mitigations that keep it trustworthy without making it rigid:
  - An evaluation set: known facts the brief should catch (INV-010, INV-099, the
    N13→N14 retraction, the M99 gap), scored across runs.
  - Citation checks: every ID in an answer must exist, and every number must
    appear in a tool result.
  - A cap of about 20 tool calls per brief, with a requirement to say what
    wasn't checked.

  My recommendation: take this version. The evaluation set is how you show the
  brief catches the right things, instead of guaranteeing it with fixed rules.
  It also matches what the brief says it's scoring: judgment, and knowing where
  confidence ends.

⏺ Agreed. Those three tools make the agent call once, read the result and call
  again. A single SELECT can't build up an analysis step by step, and
  fixed-field recall/remember mean the model fills in forms instead of
  organizing what it knows. I'd replace them with two general tools of the kind
  models are already good at using: a code workspace and a memory folder of
  files.

  1. python(code): persistent analysis workspace

  A Jupyter-like session where variables carry over between calls.

  Preloaded:
  - db: a read-only connection to the database (raw tables plus the normalized
    fact views)
  - pd: pandas
  - notes: the shift log as a DataFrame

  Returns printed output and tables, cut down if too large. Every executed cell
  is logged.

  Why it allows real agentic behavior:
  - Iterative: query, look, refine, test the next hypothesis, all in one place.
    Results from the last step are still in memory.
  - Combines sources in one step: reconcile stock, compare weeks, cross-check a
    note against invoices, and build a forecast with a stated range.
  - Covers unplanned questions: "Vendor A vs. B price," "what if demand is
    +30%," "which day ran short." No new tool needed.
  - Auditable: every number traces back to logged code.

  Guardrails: sandboxed, read-only database, no network, time limit per cell.

  2. memory: a folder of files the model manages

  Uses the same commands as Anthropic's memory tool, which current Claude models
  are trained to use: view, create, str_replace, insert, delete, rename over a
  /memories directory.

  The model decides how to organize it. It might use one file per topic
  (vendors/alder.md, open_questions.md, hypotheses.md), headers with sources and
  effective dates, and in-file "superseded" notes. That organizing is part of
  the judgment you want from the model.

  History without a rigid schema: each write is a git commit, with the reason as
  the commit message. That gives:
  - Change tracking: "Egg hold reported (N13) → retracted (N14)" is a diff with
    a reason.
  - History: "What did we believe on Oct 2?" is git show @{2026-10-02}, exposed
    as memory view --as-of.
  - Nothing is truly lost: a delete is a commit, so the old content stays in
    history.

  Readable by people: the GM and owner can open the folder and correct it
  directly. A human correction is just another commit.

  Optional 3rd tool: ask_team(question, context)

  Records a question for the GM when the data can't settle something, such as
  M99 portions, INV-099 arrival or waste weight. The brief and the next session
  show it, and an answer comes back as a new note. This makes "we don't know" an
  action, not a dead end. Leave it out if you want to stay at two tools.

  What this changes elsewhere

  - Database: stays as is (raw → normalized fact views). It's now the data the
    code reads, not the agent's whole interface.
  - Prompts (prompts.py): still fit. I'd add one line to BASE: "Use the python
    workspace to explore and test, and organize your memory directory so a
    future you can pick up where you left off."
  - Note ingest: the same loop, with a note as the prompt and memory file edits
    as the output.
  - Checks: still run after each answer: cited IDs must exist, and numbers must
    appear in the logged code output.

  Cost

  - Less control than fixed tools: the model can write sloppy analysis. The
    logged code makes mistakes easy to see, and the evaluation set catches them.
  - Infrastructure: a sandboxed Python session is more work than a SQL wrapper.
    Locally, a separate process with a read-only SQLite file is enough.

  Command: search

  ────────────────────────────────────────
  Command: write

  How memory is stored

  - /memories is a git repository. Each write or edit is one commit, with reason
    as the message and the mode and session as the author.

    when it happened in the world; the latter goes in the file text as from

  - Size: the harness warns if a file grows past 2,000 tokens, to keep files
